1. Executive decision summary
    Recommended baseline
    Build the product as a TypeScript web application using Next.js and tldraw, backed by AWS
    managed services. Use Aurora PostgreSQL for structured product data and S3/CloudFront
    for board media. Use Lambda for stateless APIs and SQS for slow/background work. Avoid
    EC2 unless a future workload truly requires a continuously running server.

The architecture is intentionally optimized for the product characteristics that matter most: a
highly interactive canvas, many user-uploaded images, fast board opening, autosave, templates,
future collaboration, and optional AI generation. The core design avoids coupling those concerns
together.

4. Target system architecture
The architecture deliberately separates the interactive editor, structured application state, media,
and background processing.

    USER BROWSER
       |
       +--> Next.js UI / tldraw editor
       |       |
       |       +--> Cognito (sign-in / tokens)
       |       |
       |       +--> API Gateway --> Lambda --> Aurora PostgreSQL
       |       |                         |
       |       |                         +--> SQS
       |       |                              +--> worker Lambda
       |       |                                   +--> transforms / exports
       |       |                                   +--> AI / email
       |       |
       |       +--> request presigned upload URL
       |                  |
       |                  +--> direct upload to S3
       |
       +--> CloudFront --> S3 optimized images / thumbnails / exports




    Critical rule
    Large media should travel directly between the browser and S3/CloudFront. Lambda should
    authorize and coordinate media operations, not proxy every image byte.

7. Media upload, delivery, and image processing
Vision boards are primarily a media-delivery problem. A fast board depends more on asset
architecture than on the database.

  UPLOAD PATH
  1. Browser asks API for upload permission
  2. Lambda validates user/board/file metadata
  3. Lambda returns an S3 presigned upload URL
  4. Browser uploads directly to S3
  5. S3 event -> SQS/Lambda image processor
  6. Processor creates optimized variants + thumbnail
  7. Asset row becomes READY
  8. Board uses CloudFront URLs


  DISPLAY PATH
  Browser -> CloudFront -> cached optimized object -> S3 only on cache miss

Database connectivity from Lambda
The API should not create uncontrolled PostgreSQL connections during traffic spikes. Use
connection pooling appropriate to the chosen Aurora configuration. RDS Proxy can be introduced
when connection churn or concurrency makes it useful. Keep functions in the same AWS region as
the database and measure connection setup separately from query time.

                      API design rule                                                     Reason


 Return only fields needed for the screen                       Serialization and transfer often cost more than the query.

 Paginate lists                                                 Avoid fetching hundreds of full records for initial render.

 Use cursor pagination for large changing lists                 More stable than deep OFFSET pagination.

 Batch related reads where sensible                             Avoid N+1 request patterns.

 Run independent backend calls in parallel                      Avoid sequential await chains.

 Return job IDs for slow operations                             Keep request latency predictable.

 Set explicit timeouts/retries                                  Prevent hidden long-tail latency.

9. Performance design and the 750-post lesson
    Key interpretation
    A 3-4 second screen for roughly 750 posts does not prove that AWS is slow. It usually means
    the request is moving, serializing, rendering, or sequentially waiting on too much data.
    Measure each segment before changing infrastructure.

13. AI-ready architecture
AI should generate normal product data rather than create a parallel AI-only representation. This
keeps generated content editable and compatible with templates, exports and collaboration.

  User prompt
    -> API creates generation job
    -> SQS worker
        -> classify themes/goals
        -> generate copy / suggested structure
        -> optional image generation/search
        -> create ordinary board objects
        -> persist board version
    -> UI receives job completion and opens editable board

19. Launch checklist
   Infrastructure is reproducible from CDK/Terraform and separated by environment.
   S3 bucket is not publicly writable; upload permissions are scoped and expire.
   CloudFront serves optimized board assets and cache headers are configured.
   Board list APIs are paginated and do not use SELECT *.
   Critical SQL queries have appropriate indexes and are measured with realistic data volumes.
   Lambda functions log endpoint/job identifiers and latency segments without leaking secrets.
   Failed background jobs go to a DLQ and can be replayed safely.
   Image processing generates multiple display sizes and stores dimensions/bytes.
   Board autosave is debounced and survives refresh/crash scenarios.
   Access-control tests cover owner/editor/viewer behavior and direct object access attempts.
   Frontend uses virtualization for any potentially large lists.
   Sentry/CloudWatch dashboards exist before public launch.
   Backups/retention policies exist for Aurora and critical S3 data.
   Cost alerts/quotas exist for AI, storage and unexpected API usage.

Appendix C. Performance investigation checklist
     Measure total API time and separate cold-start/init time from handler time.
     Measure database connection acquisition time separately from SQL execution.
     Capture exact response payload size in bytes, not only row count.
     Check query count per request for N+1 patterns.
     Run EXPLAIN (ANALYZE in safe environments) on slow SQL and verify index use.
     Inspect whether independent operations are awaited sequentially.
     Profile browser parse/render time and React commit time.
     Virtualize long lists; 750 items should not all need to be in the DOM initially.
     Check image dimensions, encoded file sizes and actual display sizes.

    Final recommendation
    Start with the smallest architecture that preserves the right boundaries: Next.js + tldraw on
    the client; Cognito, API Gateway/Lambda, Aurora PostgreSQL, S3/CloudFront and SQS on
    AWS. Keep media direct-to-object-storage, keep initial payloads small, defer realtime
    multiplayer, and let measured bottlenecks determine future infrastructure.
